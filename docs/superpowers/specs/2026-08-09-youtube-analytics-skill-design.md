# Скилл `youtube-analytics` — дизайн

**Дата:** 2026-08-09
**Статус:** утверждён (брейншторм)
**Маршрут дальше:** writing-plans → реализация (скрипты + SKILL.md) → боевой прогон по чужому и своему каналу

## Проблема

У автора есть канал на YouTube и один ролик с хорошими показателями (2000+ подписчиков и просмотры за три недели). Но хороший показатель ни к чему не привязан: непонятно, что именно сработало — тема, тайтл, вступление или случай. Повторить нельзя, потому что нечего повторять.

Под Instagram разведка есть (`instagram-analytics`), под YouTube — ничего. При этом YouTube отдаёт публично гораздо больше: тайтлы, описания, теги, длительность, Chapters, комментарии, субтитры. Всё это лежит открыто по любому каналу ниши, но руками не собирается.

Ручной обходной путь уже был — автоматизация в n8n, которая по ссылке на канал выгружала тайтлы и описания N роликов. Она решала выгрузку, но не решала главного: выгрузка не превращалась в накапливаемую базу и не отвечала на вопрос «что здесь закономерность, а что шум».

Готовых решений в реестре скиллов нет — см. раздел «Почему не берём готовое».

## Решение

Публичный hub-скилл `youtube-analytics` — разведчик YouTube-каналов. По `@handle` любого публичного канала собирает ролики с метриками, ранжирует «что залетело», считает закономерности и выгружает в структурированную базу в волте. Выборочно — разбирает вступление ролика по секундам.

Цель — не отчёт, а **сырьё для собственных роликов**: из чего сделан тайтл, который сработал, и из чего сделаны первые 60 секунд, которые удержали.

Тот же принцип, что у `instagram-analytics`: собранное всегда трактуется как **референс** для переупаковки, никогда как материал для копирования.

## Решения по развилкам (утверждено)

| Развилка | Решение |
|---|---|
| Охват первой версии | **Только публичная ветка** (Data API v3 + API-ключ). OAuth-ветка по своему каналу (CTR, показы, кривая удержания) — отдельным этапом позже, см. «Чего скилл не делает» |
| Границы скиллов | **Два скилла.** `youtube-analytics` — разведка и счёт. `youtube-meta` (позже) — тайтл, описание, теги, подсказка по превью. Та же граница, что между `instagram-analytics` и `reels-script` |
| Ранжирование | **Кратность к медиане своего типа.** Медиана считается отдельно для Shorts и отдельно для длинных; ранжируем по `median_multiple` = просмотры / медиана своего типа. Скорость (`views_per_day`) и ER остаются колонками, не критерием |
| Комментарии | **Только в `enrich`**, по выбранным роликам, топ-50 по лайкам. В `scout` — лишь счётчик (приходит бесплатно) |
| Глубина `enrich` | **Вступление дословно (первые ~60 сек с таймкодами) + Chapters + топ-комменты + разбор вступления по битам.** Полный транскрипт — по отдельной просьбе |
| Источник данных | **Гибрид:** Data API v3 для `scout` (быстро, официально, ~14 юнитов на канал), yt-dlp для `enrich` (субтитры и Chapters, которых в API нет) |
| Реализация | **CLI-скрипты** (PEP 723 + uv), а не инлайн-вызовы. Отличие от `instagram-analytics`, обосновано ниже |
| Хранение | Отдельная папка и отдельный Base, **не** сливать с инстаграмной разведкой |

## Почему не берём готовое

Реестр скиллов прочёсан по `youtube`, `youtube analytics`, `youtube data api`, `video seo`; исходники кандидатов вскрыты.

| Скилл | Установок | Что внутри | Вердикт |
|---|---|---|---|
| `zeropointrepo/…@youtube-api` | 467 | Не YouTube API, а прокси через платный TranscriptAPI.com: свой ключ + User-Agent, идентифицирующий агента | Отклонён: посредник видит, какие каналы разбираем |
| `openclaudia/…@youtube-analytics` | 434 | Настоящий Data API v3, но это 198 строк markdown — справочник curl-ручек и шаблон отчёта в чат. Ноль скриптов, ноль записи в файлы, ноль ранжирования | Отклонён: не умеет главного, пишется за час |
| `baoyu/…@youtube-transcript` | 18.7K | InnerTube + фоллбэк yt-dlp, без ключей, но нужен `scripts/main.ts` (bun/deno). 2 аудита из 3 — warn | Отклонён: yt-dlp уже стоит, TS-зависимость лишняя |
| `kostja94/…@youtube-seo` | 2.5K | Чистое знание без API, все аудиты пройдены | Отклонён: generic; свой канон в `BACKLOG.md` конкретнее |

Общее для всех: ни один не пишет в накапливаемую базу — все отвечают в чат и умирают. Плюс каждый несёт свой always-on `description`, который дрался бы за триггер с нашим скиллом. Чужой always-on в харнесе — налог навсегда.

## Три режима

Определяется по запросу. Дефолт — `scout`.

### `scout` (Tier-1 — дёшево, массово)

1. Вход: `@handle` или URL канала (можно несколько).
2. Data API: `channels` (по `forHandle`) → id плейлиста загрузок → `playlistItems` пачками по 50 → `videos` пачками по 50 (`part=snippet,statistics,contentDetails`).
3. Классификация `kind`: `short` при `duration_sec ≤ 180`, иначе `long`. Граница эвристическая (YouTube поднимал лимит Shorts до 3 минут) — записывается в допущения, при спорных случаях уточняется HEAD-запросом на `youtube.com/shorts/<id>`.
4. Считается медиана просмотров **отдельно по каждому `kind`**, затем `median_multiple` для каждого ролика.
5. Ранжирование по `median_multiple` (убыв.), внутри одного `kind`.
6. Запись в `<YT_OUTPUT_DIR>/<channel>/`: `index.md`, `cards/<id>.md`, `export.csv`. Идемпотентно по `id`.
7. Обновление `<YT_OUTPUT_DIR>/_Разведка YouTube.base`.
8. Без субтитров, без комментов, без LLM-разбора — токенов почти не тратит.

**Квота.** `search.list` не используется **никогда** — он стоит 100 юнитов из 10 000 и на своих же данных выдаёт неполную выборку. Список роликов берётся только через плейлист загрузок. Канал на 300 роликов = 1 (`channels`) + 6 (`playlistItems`) + 6 (`videos`) ≈ **14 юнитов**.

### `patterns` (Tier-1.5 — главный артефакт, почти бесплатный)

Считается по `channel.json`, сохранённому режимом `scout` (повторных обращений к API нет — режим работает офлайн по уже собранным данным). На голых метриках, без субтитров и почти без токенов. Обязательные срезы:

1. **Медиана просмотров по месяцам**, отдельно `short` и `long` — отвечает «его формат ещё работает или уже сдулся».
2. **Длина тайтла** в бакетах (≤40 / 41–60 / 61–80 / 80+ символов) vs медианная кратность.
3. **Состав тайтла** vs кратность: наличие цифры, тега свежести `(год)`, скобок, CAPS-слова, имени инструмента, вопроса.
4. **Длительность** в бакетах vs кратность (для `long`).
5. **Описание**: длина в бакетах, наличие блока таймкодов, число ссылок vs кратность. Блок таймкодов определяется регуляркой по тексту описания (`^\d{1,2}:\d{2}` в начале строки) — оно приходит уже в `scout`. Структурированные Chapters из yt-dlp появляются только в `enrich` и на этот срез не влияют.
6. **Топ-15 и дно-15 по кратности с тайтлами целиком** — из них руками выводится типология по **механике** (разрыв статуса, невероятная цифра, отрицание лидера, момент провала), а не по теме. Это самый ценный срез: механику нельзя посчитать, её видно только глазами на контрасте верха и низа.
7. **Ритм публикаций**: частота по месяцам, день недели vs кратность.

Выход — заметка `Разбор — тайтлы и паттерны.md` в папке канала, с обязательной финальной секцией **«Что забираем себе»**. Формат подтверждён практикой на `instagram-analytics`, где режим `patterns` оказался самым ценным артефактом скилла.

**Честность срезов.** Каждый срез печатает размер группы. Бакет меньше 5 роликов помечается как ненадёжный и не используется для выводов — иначе один удачный ролик превращается в «закономерность».

### `enrich` (Tier-2 — выборочно)

1. Вход: `top-N`, список `#id` или URL из уже собранной базы.
2. По каждому ролику через yt-dlp:
   - субтитры (`--write-auto-subs --sub-format vtt`, без скачивания видео) → дедуп повторяющихся строк VTT → **первые ~60 секунд дословно с таймкодами**;
   - Chapters структурой (yt-dlp отдаёт их распарсенными — руками из описания собирать не нужно);
   - топ-50 комментариев по лайкам — через Data API `commentThreads` (1 юнит на ролик).
3. **Разбор вступления по битам:** какой ход в первых 3 секундах, где обещание, где первое доказательство, на какой секунде появляется результат. Раскладка — по битам, а не пересказом.
4. Дописывает в существующую карточку, `tier2_status` → `enriched`.
5. **Грациозная деградация:** субтитров нет / отключены → поля пустые, разбор строится по тайтлу, описанию и Chapters; `tier2_status` всё равно `enriched`.

**Видео не скачиваются никогда** — ни в `scout`, ни в `enrich`. Субтитры берутся с `--skip-download`.

## Отличие от `instagram-analytics`: скрипты вместо инлайна

В `instagram-analytics` записано правило «без отдельного скрипта — вызовы инлайн». Здесь оно осознанно нарушается.

Причина: `patterns` — это арифметика по 300 записям (медианы, кратности, бакеты, срезы по месяцам). Модель, считающая медианы в уме, дороже по токенам и ошибается. Поэтому логика уходит в CLI-скрипты (PEP 723 + uv, как в `rough-cut`), а `SKILL.md` остаётся оркестрацией:

| Скрипт | Вход | Выход |
|---|---|---|
| `scripts/fetch_channel.py` | `@handle`, `YOUTUBE_API_KEY` | нормализованный `channel.json` (все ролики + поля схемы) |
| `scripts/patterns.py` | `channel.json` | готовые срезы в JSON/Markdown |
| `scripts/fetch_intro.py` | `video_id` | вступление с таймкодами + Chapters (через yt-dlp) |

Побочная выгода та же, что дал `rough-cut`: логика в скриптах — задел на веб/десктоп-обвязку, а не только на сессию.

## Схема записи

| Поле | Тип | Источник | Описание |
|---|---|---|---|
| `id` | string | API | id видео, ключ идемпотентности |
| `title` | string | API | Тайтл целиком, дословно |
| `channel` | string | API | `@handle` канала |
| `url` | string | скилл | `https://youtube.com/watch?v=<id>` |
| `kind` | enum | вычисляется | `short` (≤180 сек) \| `long` |
| `date` | ISO date | API | Дата публикации |
| `duration_sec` | int | API | Длительность (из ISO 8601) |
| `views` | int | API | Просмотры |
| `likes` | int | API | Лайки (пусто, если скрыты автором) |
| `comments` | int | API | Число комментариев |
| `median_multiple` | float | вычисляется | `views / медиана своего kind`, 2 знака. **Колонка ранжирования** |
| `views_per_day` | float | вычисляется | `views / дней с публикации`, минимум 1 день |
| `engagement_rate` | float | вычисляется | `(likes + comments) / max(views, 1)`, 4 знака |
| `description` | string | API | Описание целиком |
| `tags` | list | API | Теги (могут быть пусты для чужих каналов — проверить на прогоне) |
| `chapters` | list | yt-dlp (Tier-2) | `{start_sec, title}` |
| `thumbnail_url` | string | API | Ссылка на превью максимального разрешения |
| `tier2_status` | enum | скилл | `skeleton` \| `enriched` |
| `intro_transcript` | string | Tier-2 | Первые ~60 сек дословно, с таймкодами |
| `intro_beats` | object | Tier-2 LLM | `{hook, promise, first_proof, result_at_sec}` |
| `top_comments` | list | Tier-2 | Топ-50 по лайкам: `{text, likes}` |
| `notes` | string | пользователь | Свободные заметки |

**Открытый вопрос, решается на боевом прогоне:** отдаёт ли Data API `snippet.tags` для чужих каналов. yt-dlp по ролику Сараева вернул 46 тегов; подтверждения, что API делает то же для не-владельца, найти не удалось. Если поле окажется пустым — теги переезжают в Tier-2 (yt-dlp), а срез «состав тайтла» это не затрагивает.

## Выгрузка

```
<YT_OUTPUT_DIR>/
  _Разведка YouTube.base          ← Obsidian Base: все карточки YouTube в одном срезе
  <channel>/                      ← подпапка на канал (@handle без @)
    index.md                      ← ранжированная таблица, раздельно Shorts и длинные
    Разбор — тайтлы и паттерны.md ← артефакт режима patterns
    cards/<id>.md                 ← карточки
    export.csv                    ← плоский full-schema артефакт
    .channel.json                 ← сырая нормализованная выгрузка, вход для patterns
```

`.channel.json` — служебный файл (с точки, чтобы Obsidian его не показывал): он нужен, чтобы `patterns` считал офлайн и не тратил квоту повторно.

`index.md` — две таблицы (Shorts и длинные), в каждой колонка «Тема» = кликабельная ссылка `[[cards/<id>\|<title>]]`. Первая колонка Base — `file.name`, иначе строки не кликаются.

**Отдельно от инстаграмной разведки.** Поля разные (`kind`, `duration_sec`, `chapters`, `median_multiple`), метрики между платформами несопоставимы — общая таблица была бы мусором, а не кросс-платформенным срезом.

## Что переиспользуется из существующих скиллов

| Скилл | Что берём | Оговорка |
|---|---|---|
| `instagram-analytics` | Архитектуру целиком: двухуровневость, контракт выгрузки (`index.md` + карточки + CSV + Base), папка на автора, идемпотентность по id, дисциплина ответа, правило «видео не храним» | Меняется источник и набор полей |
| `brand-voice` | **Закон текста** (`copy-law.md`) при чтении тайтлов: результат вместо термина, свойство→выгода | В разведке применяется как **линза для оценки чужого**, не для написания своего |
| `hook-base` | Склад хуков — вступления из `enrich` кладутся операцией ПОЛОЖИТЬ | Нужен новый `формат: youtube-intro`: хук ролика живёт в паре с тайтлом и превью, а не соло |
| `reels-script` | Shorts как формат короткого видео | Только на хэндоффе, логика не дублируется |

**Что осознанно не подключаем:** `post-hq` (описание YouTube — не пост, оно не читается подряд и не имеет CTA-механики поста; пятая платформа размыла бы его контракт) и `content-machine` (оркестратор подключают к устоявшейся ветке, а не к строящейся).

## Голос и описание: ответ на вопрос автора

Вопрос был: применим ли `brand-voice` к описанию, если описание — шаблонная история.

Ответ уже записан в самом `brand-voice` ([SKILL.md](../../../skills/brand-voice/SKILL.md), таблица двух слоёв): **закон** применяется везде, **голос** — только там, где говорит автор. Описание YouTube по этому правилу распадается на три части, и они разные:

1. **Первые ~125 символов** (видны в поиске и под плеером) — работают как обложка карусели. Закон обязателен: результат вместо термина. Подтверждено дважды на своих же данных — гейт обложки в `carousel-backbone.md` и тест хука в `reels-script/SKILL.md`. Голос не нужен.
2. **Абзац «если ты впервые, я…»** — здесь говорит автор. Голос нужен целиком.
3. **Ссылки, Summary, Chapters, инструменты** — чистый шаблон-константа. Ни закон, ни голос не применяются.

Вывод для `youtube-meta`: подключать `brand-voice` не «к описанию», а **посекционно, по правилу, которое в нём уже написано**. Ничего не ломается — скилл сам знает, где ему молчать.

## Ключи и приватность

- Один новый ключ — `YOUTUBE_API_KEY` (Google Cloud → включить YouTube Data API v3).
- `.env` в папке скилла, gitignored, как у `instagram-analytics`; `.env.template` в репо.
- Переменные: `YOUTUBE_API_KEY`, `YT_OUTPUT_DIR` (дефолт `./youtube-analytics-output`, override — мостик в волт).
- **Никаких сторонних сервисов-посредников:** только `googleapis.com` и локальный yt-dlp. Ни один скилл сообщества не устанавливается.
- Чтение `.env` — без `source` (зафиксировано в `instagram-analytics/references/apify.md`: zsh ломается на значениях с пробелами).

## Чего скилл не делает

- **Не считает CTR, показы, удержание и watch time.** Публичный Data API их не отдаёт ни по какому каналу — это OAuth-ветка (Analytics API, `audienceWatchRatio` × `elapsedVideoTimeRatio`), только по своему каналу, вторым этапом. По чужому каналу удержание недостижимо в принципе, никаким инструментом. Это должно быть сказано пользователю прямо, а не подразумеваться.
- **Не пишет тайтлы, описания и теги** — это `youtube-meta`.
- **Не качает видео.**
- **Не ищет по ключевым словам и нишам** — `search.list` слишком дорог по квоте.
- **Не даёт объёмы поисковых запросов** — их нет в API; выдумывать цифры запрещено.

## Хэндофф

- `patterns` → `youtube-meta`: канон тайтла и структура описания уже лежат в [BACKLOG.md](../../../BACKLOG.md) (запись про `youtube-meta`), эталон структуры описания — разбор Ника Сараева.
- Вступления из `enrich` → `hook-base`, операция ПОЛОЖИТЬ, формат `youtube-intro`.
- Shorts → `reels-script`.
- База — самостоятельный артефакт и сид для сравнения «свой канал vs канал из ниши».

## Критерии готовности

1. `scout` по каналу Ника Сараева отрабатывает и укладывается в квоту (проверить фактический расход).
2. `scout` по своему каналу отрабатывает тем же путём.
3. `patterns` выдаёт все семь срезов, помечает ненадёжные бакеты, заканчивается секцией «Что забираем себе».
4. `enrich` по топ-3 достаёт вступление с таймкодами и Chapters; при отключённых субтитрах — деградирует без падения.
5. Повторный `scout` по тому же каналу не плодит дубли (идемпотентность по `id`).
6. Карточки открываются в Obsidian, ссылки в `index.md` и Base кликабельны.
7. Скилл добавлен в `skills/README.md` и подключён глобально через `install-skills.sh`.
